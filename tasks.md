# TritonTrace — Frontend Task Plan

Working branch: `user_model_app`. This plan follows `CLAUDE.md`: seeded/in-memory data only, no backend/ML calls, small focused components, no unrelated rewrites.

Execution model: each numbered task below is done **one at a time**. Before starting a task we confirm scope/approach; after finishing it we report what changed and how to verify, then wait for a go-ahead before starting the next one.

---

## Context / findings from inspection

- `data/` contains two real satellite oil-spill runs: `ow-0008` and `ow-0009`, each with:
  - `AIS_top15_vessels.csv` — top 15 correlated vessels (MMSI, name, type, score, encounter coords, etc.)
  - `possible_source_origins_top.csv` / `possible_source_origins.csv` — hindcast candidate origins (lat/lon/support_score/…)
  - `frontend_files/` (or `frontend-files/` for ow-0009): `initial_particles.csv`, `final_particle_positions.csv`, `support_density_grid.csv` — the particle/hotspot data
  - `source_origin_summary.txt` — human-readable summary (centroid, uncertainty radius, T0 timestamp, etc.)
- The admin portal (`InvestigatorPortal.jsx` → `TriageQueue.jsx`) currently lists **hardcoded mock incidents** from `src/utils/mockData.js` (`mockHistoricalIncidents`, `mockIncident`).
- The AIS "top suspects" panel (`AisCorrelationMatrix.jsx`) currently renders a **hardcoded `mockSuspects` array of 3 vessels**, unrelated to any incident.
- The hotspot/hindcast visuals (SAR polygon, hindcast particle layer) in `MapCanvas.jsx` are also **hardcoded** (fixed polygon coords, 2 fixed hindcast points), independent of `IncidentContext`'s `hindcastData` (1000 generated particles around a fixed centroid) which is what `HindcastController.jsx` actually animates.
- There's already a live vessel/trajectory pipeline: `IncidentContext.jsx` parses `src/utils/east_med_massive_random_ais.csv` via PapaParse into `commercialFleet` (currently sliced to top 10), which `MapCanvas.jsx` renders as `ais_tracks-source` (lines) + `live-vessels-source` (triangle markers). This is the mechanism we'll extend for AIS vessel trajectories.
- `src/data/incident1/*.json` existed previously and were deleted (per `git status`) — no active code currently imports them, so nothing to reconcile there.

## Task 2 (done) — Show each incident's top-15 AIS vessels + 20 extra vessels as trajectories on the map

**Goal:** Render on the map, for both incidents at once (same always-shown pattern as Task 1.5): the 15 correlated AIS vessels from each incident's `AIS_top15_vessels.csv`, plus 20 vessels per incident geographically nearest to its origin (sourced from the existing `east_med_massive_random_ais.csv` pool already parsed in `IncidentContext`) — all as trajectory lines + vessel markers, reusing the existing `ais_tracks-source` / `live-vessels-source` map layers.

What was built:
1. `src/data/aisTopVessels.js`: parses each incident's `AIS_top15_vessels.csv` into `{ "ow-0008": [...], "ow-0009": [...] }` (rank, mmsi, name, type, score, min distance, best-encounter coords). All 15+15 top vessels turned out to have real matching trajectories in `east_med_massive_random_ais.csv` (verified by MMSI), so no placeholder/synthesized trajectories were needed.
2. `IncidentContext.jsx`: the AIS pool parse now also keeps the full uncapped list (`allVesselTracks`, 2003 vessels); a new `incidentVesselFleet` combines, per incident, its real top-15 (by MMSI match) + the 20 nearest pool vessels by geography (via `turf.distance` from the incident's coordinates), de-duplicated across both incidents. The original capped `commercialFleet` (used by the separate Commercial Operator portal) was left untouched so that portal's behavior doesn't change.
3. `MapEngine.jsx` (the admin/investigator map wrapper only) now passes `incidentVesselFleet` into `MapCanvas` as its `commercialFleet` prop, and defaults the "AIS Vessel Tracks" layer to active so it's visible immediately, matching Task 1.5's always-shown pattern.
4. `AisCorrelationMatrix.jsx` now takes an `incidentId` prop and renders that incident's real top-15 list (name, MMSI, type, score, min distance to origin, intersect coordinate) instead of the old hardcoded 3-vessel mock; `TriageQueue.jsx` passes `incidentId={report.id}` so each card's panel shows its own incident's suspects.
5. **Bug fix found and fixed along the way**: every `MapCanvas.jsx` effect that synced live data into the map (SAR slick, AIS tracks, drawn polygon, diversion route) and the layer-visibility effect were gated on `map.isStyleLoaded()`, which this app's Mapbox instance reports as `false` indefinitely long after the style is actually ready — so none of these updates were ever actually reaching the map after initial mount. Replaced the gate with a direct `map.getSource(id)`/`map.getLayer(id)` existence check (the real precondition), which is what let the AIS vessels — and Task 1.5's particles — actually render.
6. **Follow-up (done)**: AIS trajectories are now clipped to each incident's own 72-hour hindcast window (T0 minus 72h to T0 — e.g. ow-0008: 2019-06-11 20:35:58 to 2019-06-14T20:35:58, matching `final_particle_positions.csv`'s own checkpoint range), not shown as full-year tracks. Implemented in `IncidentContext.jsx`: the raw AIS parse keeps each vessel's timestamped pings; `clipVesselToIncidentWindow()` re-derives a vessel's trajectory/current-position using only pings inside its assigned incident's window, dropping vessels with no pings in that window. Applied per incident (not a single hardcoded date range), since ow-0008 (June 2019) and ow-0009 (April 2019) have non-overlapping windows — a global range would have zeroed out one incident's vessels entirely.
7. Verified in-browser (Playwright): both incidents' vessel tracks (70 combined, 35 per incident, no overlap) render on the map by default; the AIS Correlation Matrix panel shows each incident's real top-15 vessels (verified `ow-0008` vs `ow-0009` show different vessel names); a sampled vessel's trajectory shrank from 38 unclipped pings to 32 within its incident's window, confirming the clip; zero console errors; Triage Queue and ATTRIBUTION flow regression-clean.
8. **Follow-up (done)**: the "20 nearest" extras looked unnaturally clustered right on top of the origin (closest 20 were all within ~6-25km, bunched to one side). Reworked the selection in `IncidentContext.jsx`: vessels within `EXTRA_VESSELS_MIN_DISTANCE_KM` (15km) of the incident are excluded, then one nearest-beyond-that-radius vessel is picked per 18° compass sector (20 sectors, via `turf.bearing`) so the extras ring the incident evenly across all directions instead of bunching. Window-clipping is applied *before* the distance/sector selection now (not after), since picking the geometrically-nearest vessel per sector first and clipping afterward could pick a vessel with zero pings in that incident's window and silently lose a slot — this had briefly regressed the fleet from 70 down to 31 vessels during testing before the fix. Re-verified: fleet count back to 70, extras now span ~18-150km across 19/20 compass sectors per incident (previously 6-25km, one-sided).

Data prep already done:

At 1.78MB / 1.2MB, these will be lazily fetched only when FORWARD TRACK is first opened (same `?url` + `Papa.parse({download:true})` pattern already used for the AIS pool CSV), not bundled eagerly like the smaller CSVs.
- `hotspot_status_timeline.csv` copied as-is (small, 11 hotspots × 73 hourly statuses) — confirmed its 11 `hotspot_name` values match `regional_alert_geofences.json`'s `name` field, except "Port Said (Suez Canal)" vs. "Port Said (Suez Canal Entrance)" (needs one normalization mapping).

What was built:

Flagging this now rather than overselling what a 7-feature geometry model trained this way can actually do.

What was built — new `src/lib/itopfLiability.js` (pure functions, no component code):

When a route intersects multiple zones, the highest multiplier wins (most conservative estimate).
5. `computeVesselLiability(trajectory, slickAreaSqKm)` — ties it together: `Total Liability = (mass_kg * $50) * hotspot_multiplier`, returning `{ massKg, itopfTier, baselineLiabilityUsd, hotspotMultiplier, threatenedAsset, totalLiabilityUsd }` (the "JSON payload" the spec asked for).
6. `formatUsdCompact` — "$49.94M" style display helper.
